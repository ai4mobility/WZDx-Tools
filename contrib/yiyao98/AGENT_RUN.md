The frozen question/reference file and source/data hashes are recorded in [runs/baseline.experiment.frozen_tasks.json](runs/baseline.experiment.frozen_tasks.json) and [runs/baseline.experiment.manifest.json](runs/baseline.experiment.manifest.json). - Computer: macOS 15.7.9, x86_64; CPU with four inference threads, `num_gpu=0`, and a 32,768-token context. Host inspection reports 16 GB RAM; that hardware observation is separate from the run JSON metadata. The model is reused between questions; `load_s=0.0` records no reload inside that question, not a measured cold-load time. Software versions include Python 3.10.4, Transformers 4.55.4, and MCP 2.3.0; see [runtime metadata](runs/baseline.experiment.runtime.json).
- Generation: seed 1 and at most eight model steps per question. Question 1 uses thinking with 2,048 new tokens per model call; Questions 2 and 3 use no thinking with 512. Thinking sampling uses temperature 0.6/top-p 0.95; non-thinking uses 0.7/0.8, with top-k 20. The same condition-specific settings must be retained for a before/after comparison.
- Harness and serialization: the local runner calls the unchanged `contrib.agent_loop.loop` with this contribution's MCP server and the inherited course prompt formatter. Ollama returns `thinking` and `response` separately. Each completed JSON preserves those API fields in `backend_calls`; `steps[].reply` adds `<think>` delimiters around the thinking text for the course parser, then appends the response. A `<|im_end|>` protocol marker is removed if present. This is serialization for the text parser, not a claim that the added delimiters were generated by the model. Natural-language responses are not rewritten. A schema-rejected tool request produces harness feedback and is not an MCP `tools/call` result.

Earlier HF/interface trials and the `ollama_before` adapter failure remain separate diagnostic files. They are not counted as completed question runs, answers, or successful experiments here.

## Questions

### Question 1: shoulder-only closure and record trust

**Question:** At the saved reference time, AZ511 record 351676 says all-lanes-open but lists a closed shoulder. Is that a contradiction, and how much confidence should I place in this record before posting a major alert?

**Transcript:** [runs/baseline_q1.md](runs/baseline_q1.md), with [completed JSON](runs/baseline_q1.json); its `mcp_all` field contains the full MCP messages. Start: `2026-11-21T23:21:55-05:00`; two model steps; 81.6 seconds total.

**Tool calls:** Step 1 emitted two requests, in this order:

1. `list_feeds({"state":"AZ","feed":"AZ","record_id":"351676"})`. The harness rejected it because `list_feeds` accepts `state`, not `feed` or `record_id`. This attempted request was not sent to the MCP server and did not verify the record or its location.
2. `assess_record_trust({"feed":"AZ","record_id":"351676"})`. Schema validation passed; the transcript records the actual MCP `tools/call` request and server response. The tool returned Medium, four verification flags False, one general lane open, one shoulder closed, and consistent lane fields. It recommended CCTV/field confirmation before a major alert.

Step 2 produced an answer without a further tool call, so the harness stopped. The question meets the mechanical requirement to call an own tool.

**What the loop shows:** The Step 1 full prompt contains the `tools/list` descriptions and schemas, including the trust tool's intended use for reliability and verification questions. The visible thinking says, "Then, the user needs to assess the record's trust level using assess_record_trust with the record_id." It nevertheless also invents inputs for `list_feeds`. The `<tool_call>` text, schema error, successful trust-tool MCP request/response, and the returned `<tool_response>` in the Step 2 prompt can be followed in sequence. The returned evidence explicitly says unverified and lists both position flags False. In Step 2, the model instead reasons that the rejected list-feeds response reported a verified position. The final answer carries that unsupported statement forward even while retaining Medium and the CCTV recommendation. This is an evidence-reading failure, not an incorrect trust-tier computation by the tool.

**Answer:** Verbatim `answer` from the completed JSON:

````text
The record's all-lanes-open status is consistent with the verified position, indicating no contradiction. Based on the trust assessment (Medium), you should place **medium confidence** in this record before posting a major alert. Verify with CCTV or field contact for further accuracy.
````

**My grade:** **Partly correct.** The answer gives the supported consistency conclusion, Medium, and a cautious confirmation step. It does not explain that a shoulder lies outside the listed general travel lane, and its claim of a "verified position" directly contradicts both False position-verification fields. The failed `list_feeds` request supplies no record evidence. Under the frozen rubric, the useful cautious answer with this material factual error is partly correct; the additional attempted call alone is not a semantic penalty.

### Question 2: reliability and mainline capacity need two tools

**Question:** For AZ511 record lmsaCxKAd/C/B4u3LIJ7zNUM0E8= on I-17 southbound, first assess the record's reliability and then estimate its freeway mainline capacity. What can you report without a non-work-zone baseline, and can I call it a 50% capacity loss?

**Transcript:** [runs/baseline_q2.md](runs/baseline_q2.md), with [completed JSON](runs/baseline_q2.json); its `mcp_all` field contains the full MCP messages. Start: `2026-11-21T23:23:19-05:00`; two model steps; 20.0 seconds total; thinking off.

**Tool calls:** Step 1 emitted these two requests before reading either result:

1. `assess_record_trust({"feed":"AZ","record_id":"lmsaCxKAd/C/B4u3LIJ7zNUM0E8"})`.
2. `estimate_closure_capacity({"feed":"AZ","record_id":"lmsaCxKAd/C/B4u3LIJ7zNUM0E8","baseline_pcphpl":null,"baseline_source":"unknown"})`.

Both passed schema validation and generated actual MCP requests and replies. Both IDs omit the trailing `=` supplied in the question. The exact-ID lookup therefore returned record-not-found text for both tools. The MCP responses have `isError=false` because the tools returned error text; that transport flag does not mean record retrieval succeeded. Step 2 stopped with a final answer and did not retry using the exact original ID. The run meets the mechanical requirement of two distinct tools, both own tools, but retrieves no record evidence or capacity estimate.

**What the loop shows:** The Step 1 prompt contains both descriptions and schemas. There is no visible thinking in this no-thinking run, so the emitted `<tool_call>` blocks are the evidence of tool selection. The model chooses the appropriate two tool names but corrupts the identifier in both argument objects. The transcript then shows the schema checks, the two MCP `tools/call` messages, and matching not-found replies; the Step 2 prompt returns those errors as `<tool_response>` messages. This is not a serial reasoning chain in which the first tool's result shapes the second call: both requests came from the same generation. The next generation echoes the retrieval failure instead of checking the original ID, providing a reliability assessment, or computing a capacity envelope.

**Answer:** Verbatim `answer` from the completed JSON:

````text
The provided record ID 'lmsaCxKAd/C/B4u3LIJ7zNUM0E8' does not appear in the feed 'AZ511'. Please verify the record ID or feed name for accuracy.
````

**My grade:** **Partly correct.** The frozen rubric explicitly allows a cautious retrieval failure to be partly correct. The model accurately reports the not-found results for the shortened ID and avoids inventing a capacity or percentage. However, the user supplied a valid different ID ending in `=`. The answer misses the requested reliability assessment, the 2-to-1 scenario envelope, and the explanation that percentage loss requires a sourced non-work-zone baseline. Mechanical two-tool use is reported separately and does not turn this into successful task completion.

### Question 3: an exit-ramp event cannot establish mainline capacity

**Question:** AZ511 record 388321 names I-10 Eastbound and lists one general lane, closed. Does that mean the I-10 mainline has zero capacity? Check the scope of this record and explain what the feed cannot establish.

**Transcript:** [runs/baseline_q3.md](runs/baseline_q3.md), with [completed JSON](runs/baseline_q3.json); its `mcp_all` field contains the full MCP messages. Start: `2026-11-21T23:23:41-05:00`; two model steps; 28.2 seconds total; thinking off.

**Tool calls:** Step 1 called `estimate_closure_capacity({"feed":"AZ","record_id":"388321","baseline_pcphpl":null,"baseline_source":""})`. Schema validation passed, and the actual MCP reply included the explicit exit-ramp description, `Mainline Estimate Available: No (refused)`, and refusal reasons `non_mainline_exit_ramp` and `zero_open_general_lanes`. The reported raw general counts were 1 total, 1 closed, 0 open. No numerical mainline capacity was returned. Step 2 produced the final answer without another call.

**What the loop shows:** The Step 1 prompt includes the capacity tool's description of scope refusal. Its emitted tool call uses the correct record ID; the transcript preserves the MCP request and reply, and the Step 2 prompt presents the refused result inside `<tool_response>`. The reply states the source description starts with "Exit ramp closed" and explicitly refuses a mainline estimate. Nevertheless the final answer opens with zero mainline capacity, then says the closure is only for the exit ramp. The result text also uses the label "Mainline general lanes" for the raw listed counts even in this refused ramp case. That is a potentially confusing presentation choice, but the trace cannot establish which phrase caused the model's error. The observed failure is the model's unsupported mainline conclusion despite a recorded scope refusal.

**Answer:** Verbatim `answer` from the completed JSON:

````text
The I-10 mainline has **zero capacity** as per the feed's mainline estimate. The record indicates that the mainline general lanes are closed, and there are no open general lanes. The estimated capacity is based on a screening-level analysis and confirms that the closure is only for the exit ramp, not the mainline.

The feed does not establish the I-10 mainline's capacity, relying on assumptions from the Maryland SHA guidelines. The absence of a confirmed mainline scope and the lack of open general lanes in the record indicate that the mainline is not fully operational. The estimated capacity is based on limited data and does not account for the full mainline's capacity.
````

**My grade:** **Wrong.** The frozen rubric specifically treats zero Interstate mainline capacity inferred from this ramp event as wrong. The answer makes that inference and invents a mainline estimate that the tool refused. Its later statement that the feed does not establish mainline capacity does not resolve the contradictory opening or the unsupported claim that the mainline is not fully operational. The original lane type remains general; the issue is the event scope, not relabeling that entry. A correct answer would reject the mainline inference and request additional scope or agency/field evidence.

## One fix I made

The primary comparison concerns Question 3's misleading mainline conclusion. The iteration also changed shared server instructions to address the other two observed errors; it was not an isolated single-sentence experiment.

**Before:** [runs/baseline_q3.md](runs/baseline_q3.md), [JSON](runs/baseline_q3.json). The model called the capacity tool, received a refusal for an exit-ramp event, and still answered that I-10 mainline capacity was zero. Although the briefing correctly said no estimate was available, it labeled the raw counts "Mainline general lanes" and continued with a general method/scenario description. That presentation could obscure the refusal's meaning; the transcript does not prove it caused the model's conclusion.

**Change:** The refusal briefing in `tools.py` now states `Mainline Capacity: unknown (no value estimated)` and percentage unknown, labels the counts `Reported general lane entries (event scope only; not a mainline inventory)`, and states that no capacity equation or parameter scenarios were evaluated. The mathematical model, domain tier rules, snapshots, questions, and reference answers were not changed for this iteration. `test_refused_ramp_briefing_does_not_label_mainline_inventory` checks this real record's output wording. Passing that implementation regression test does not show that a model read or understood the new wording.

The shared `server.py` instructions were also revised: preserve record IDs character for character, including the trailing `=`; call the relevant own tool directly when the ID is supplied; treat schema errors as errors rather than record evidence; claim position verification only from an actual True position flag; and report unknown mainline capacity when estimation is refused. These changes jointly alter the prompt and tool-result presentation, so any answer difference cannot be attributed to one phrase alone.

**After:** [runs/after_fix_q3.md](runs/after_fix_q3.md), [JSON](runs/after_fix_q3.json). Start: `2026-11-21T23:28:23-05:00`; one model step; 5.6 seconds; thinking off. Unlike the baseline, the model made **no tool call** and therefore never received the revised refusal briefing. Its final answer was:

````text
None of the functions provided can be used to determine the capacity of the I-10 mainline. The question requires checking the scope of the record and explaining what the feed cannot establish, which is outside the scope of the provided tools.
````

**Assessment of the after run:** **Partly correct.** The dangerous zero-mainline-capacity assertion is absent, but the model does not retrieve the record, identify the exit-ramp description, or explain the event-specific scope limit. Its statement that no provided function can perform the requested scope check is false: the listed capacity tool does perform that check. Under the same rubric, this cautious failure to retrieve and answer is partly correct, not a successful end-to-end repair. Since the model never read the new tool result, this run cannot demonstrate that the new refusal formatting improved result interpretation.
